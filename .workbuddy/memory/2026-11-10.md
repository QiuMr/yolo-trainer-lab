## 项目现状梳理（首次建档，此前无记忆日志）

目标（PLAN.md）：任意显卡可训练的 YOLO26n 训练器，exe 几十 MB，用户零配置（不装 CUDA/ROCm）。

### 已完成（此前未记录）
- `research/montgomery`、`research/burn` 均已克隆（montgomery commit 0b17bf9，工作区干净未改代码）。
- montgomery 用 `cargo build --release` 在 Windows 构建成功三次：
  - `artifacts/target/release/montgomery.exe` = **144,057,344 B（137 MB）**，耗时 17m43s
  - `artifacts/target-dist/release/montgomery.exe` = **134,327,296 B（128 MB）** + pdb 11 MB，耗时 40m31s
  - `artifacts/target-slim` 构建进行到 `Compiling montgomery` 后中断，**无产物**（slim 参数未知）
- 日志为 PowerShell 转存，尾部是 UTF-16 混合，需 iconv 才可读。

### 关键结论 / 风险
1. **许可：montgomery 是 AGPL-3.0**（README 与 Cargo.toml 均已确认）。PLAN.md 里还是"待确认"。
   闭源商业分发基本不可行；SaaS 也要开源服务端。这是方案 A 的硬障碍，优先级高于技术指标。
2. **体积与目标差 3–4 倍**：134 MB vs "几十 MB"。rlib 体积 top5：
   cubek_matmul 93 MB、turso_core 89 MB、burn_cubecl 86 MB、montgomery 本体 85 MB、
   pliron_spirv 78 MB、burn_flex 77 MB。
   - `turso_core`（SQLite 重写）是 **cubecl-common 的编译缓存依赖**，由 `Burn.toml` 的
     `[cubecl.compilation] cache = true` 拉起 → 关掉缓存可能砍掉这一坨，**未验证**。
   - wgpu 的 shader 栈（pliron/tracel/ash/naga）约 180 MB rlib，属硬成本。
3. **模型准备链路目前断开**：仓库内只有 `tests/assets/hot-dog-classifier.bpk`，**没有 yolo26n.bpk**；
   需要 Python + uv + ultralytics 8.4.117 + torch 走 `tools/export_checkpoint_state.py` → `montgomery pack`。
   而 MODEL_BRINGUP.md 引用的 vendored `../ultralytics` 目录**不存在**（已查 research/ 下只有 burn、montgomery）。
4. **feature 门槛**：`default = ["pretrained","onnx"]`，`training` 需显式开启（连带 gpu/wgpu/cubecl/autodiff）。
   历史上 144 MB 那版应未带 training 或带了不同组合，需确认，否则体积对比无意义。
5. 性能数据均来自上游自测（RTX 5080，Vulkan，3 epoch × 32 图），**本机无实测基线**。
   上游结论：640 分辨率普遍比 Ultralytics 快 1.07–2.01×，1280 反而多数落后；VRAM 占用更高。

### 空缺
- `docs/` 与 `spikes/` 全空 —— 所有结论从未落盘。
- 无任何 GPU 兼容性冒烟（NVIDIA/AMD/Intel 均未测）。
- 无 `predict`/`train` 实跑记录（连 hot-dog-classifier 都没跑过）。

## 下午：全链路跑通（重要进展）

**用户决策**：AGPL 许可与 134MB 体积均可接受 → montgomery 直接作为主方案，不再重写 Burn。

### 已实测通过（详见 docs/STATUS.md）
| 环节 | 结果 |
| --- | --- |
| 分类推理 CPU | ✅ not_hot_dog 96.92% |
| 分类推理 GPU | ❌ device lost |
| 训练 dry-run CPU | ✅ Device<Flex(Cpu)> |
| 训练 1 epoch CPU | ✅ loss 4573.58，checkpoints + exports 齐全 |
| 训练产物推理 | ✅ 输出检测 + 标注图 |

**训练产出的 best.bpk = 4.98 MB**；exe（training 全功能）= 134 MB。

### 关键代码改动（三处，均为本地实验）
1. `research/montgomery/src/lib.rs` 加 `wgpu_device_from_env()`，支持
   `MONTGOMERY_WGPU_BACKEND=dx12|vulkan|gl|cpu`（cpu 仅诊断，让 train 落到 Flex）。
2. `spikes/cubecl-wgpu-patched/` = cubecl-wgpu 0.11.0 副本，`runtime.rs:693` 加
   `CUBECL_WGPU_TIMING=system` 开关，默认行为不变。
3. `research/montgomery/Cargo.toml` 加 `[patch.crates-io]` 指向该副本。
4. `spikes/tiny-dataset/` = 4 训练图 + 2 验证图的最小 YOLO 数据集（3 类）。

### 技术结论
- **崩溃根因**：`cubecl-wgpu/src/runtime.rs:693` 用 adapter 的 `TIMESTAMP_QUERY`
  声明决定 Device 计时；驱动声明支持但 map 回读失败 → autotune profiling 崩 → device poison。
- **DX12 路线已放弃**：burn-wgpu 0.22 只有 vulkan/metal/webgpu feature，无 dx12；
  底层枚举虽存在但缺 shader 后端，实测创建设备后挂起。
- **本机 GPU 不可用于训练**：MECHREVO WUJIE 14 / Ryzen 5 5560U / Vega 6 核显（共享内存）/ 16GB。
  修掉 timings 后仍 device lost；dry-run（batch1/160px）240s 未完成，疑 JIT 编译极慢。
  系统日志无 TDR 记录。→ 需在独显机器上验证真实场景。
- 增量编译经验：只改 montgomery 本体 2m11s；改 cubecl-wgpu 后 7m56s；
  用 `--target-dir artifacts/target-dist` 复用依赖是关键。

### 环境坑
- PowerShell 5.1 执行 cargo 时 `2>&1 | Select-String` 会把输出吞掉，改用 bash 跑 cargo 正常。
- MSYS `printf` 写含 `\n` 的 YAML 会产出 `/n` 字面量，配置文件一律用 Write 工具写。

**两个值得记住的实现细节**：
1. 绝对定位的 `inset-x-0` 是相对**padding box** 算的，所以侧栏药丸会等于整条 rail 宽、两侧没有留白。
   要么显式写 left/right，要么把 padding 放到内层。这个坑在药丸上真实出现过一次。
2. 日志用数组下标做 key，`slice(-400)` 一裁剪就从头部丢元素 → 整列表重新挂载 → 所有行重放
   淡入动画。日志类列表必须用单调 id 做 key。

**验证方式（可复用）**：无头 Edge 截图时加 `--force-prefers-reduced-motion`，否则
`animation-delay` 错峰的卡片会停在 opacity 0，看起来像"元素没渲染"（本次误判过一次，
一度以为第 4 张指标卡丢了，实际是截图时机落在动画延迟内）。

**待人工确认**：拖拽调宽、横滑切页、长按提示、拖文件夹进窗口——这些需要真实指针事件，
无头浏览器验不了，也不要拿 CDP 合成事件冒充（不带 pointerType，测不到触摸分支）。

### 后续：手势实测（同日 20:00）

**真机 UI 自动化踩坑**：`mouse_event`/`SetCursorPos` 合成的输入对以管理员身份运行的应用**静默失效**
（UIPI 拦截，低完整性进程不能向高完整性窗口注入输入）。表现极具误导性：窗口在、前台在、
截图正常，就是不响应点击——很容易误判成"手势代码没生效"。

**换 CDP 驱动浏览器预览**（`spikes/qa/cdp_browser.py`）：`Input.dispatchMouseEvent` 发真实的
mouse/pointer/wheel 事件，再把结果从 DOM 读回来（input 的值、aside 的宽度、h1 的文本）。
比截图验证可靠得多，而且不需要每次改代码都等 3.5 分钟的 tauri 重编译（vite build 2 秒）。

实测拿到的数据：拖 80px → 100 变 140；拖边缘 236 → 296；横滑 deltaX +40×5 → 训练到监控。

**抓到一个真 bug**：`useSwipe` 里 `reset()` 在 `if (accX > 0)` 之前执行，累加器被清零，
所有横滑都走 else 分支（永远回退）。静态看代码完全正常，是"日志说 left、调用栈指向
onSwipeRight"这种矛盾才逼出来的。**教训：读累加器之前不要清零；分支判断要先取局部变量。**

**另一个教训**：无头截图验证动画时一定要加 `--force-prefers-reduced-motion`，否则
`animation-delay` 错峰的元素会停在 opacity 0，看起来像没渲染（本次误判过第 4 张指标卡）。

### 侧栏选中态两个 bug —— 同一个根因（22:00）

用户报「选中后不居中、偏下」和「点设置后设置菜单消失、跳回数据集」。

**根因**：药丸位置用的是 `row.offsetTop`。`offsetTop` 相对**最近的 positioned 祖先**，
而侧栏有两个分组（主 `nav`、底部 `pinned` 容器）**各自都是 `relative`**，于是：
- 主列表的行 offsetTop 从 `nav` 顶部算，漏掉整列的 `pt-1.5`（6px）→ 药丸整体偏上 6px，
  图标文字在黑块里看起来就偏下；
- 设置行在 `pinned` 容器里 offsetTop = 0 → 药丸飞回顶部；同时该行因为 `active` 变成白字，
  落在白底上真的看不见 → 用户看到的是"设置没了，数据集被选中"。

一个 bug 两个现象，修法只有一处：**用行与整列的 `getBoundingClientRect` 之差**（再减
`clientTop`），外加 `ResizeObserver` 重新测量，不再假设行高固定。

**可复用教训**：`offsetTop` 只在 offsetParent 唯一时才等于"在容器里的位置"。
分组布局里一律用 rect 差。

**另一个坑**：`--screenshot` 外部截图 + `--force-prefers-reduced-motion` 时，设置行的白字
被截成纯黑块，让我以为层级错了，白查了半小时 z-index。**同进程 CDP `Page.captureScreenshot`
才是准的**，外部 `--screenshot` 对动画结束态不可靠。

### AI 操控接口（23:00）

`control.rs` 手写 HTTP（不引 axum/tokio，理由见 D017），`runstate.rs` 折叠事件，
`runtime.rs` 作为两侧共享状态。设置页新增「AI 操控」卡片（打码 token + 一键复制提示词）。

实测：18 项全过，真实跑 2 epoch（loss 4573.58 → 4072.84，1.4s/epoch），best.bpk 落盘；
409 并发、中止变 failed、端口切换/关闭即时生效、重启 token 不变。

**环境坑（会误导任何人）**：本机 `http_proxy=127.0.0.1:47479`。curl 把
`http://127.0.0.1:47821` 也发给代理 → `502 upstream connect failed` / `10061`，
**看起来完全像服务没起来**，实际进程在监听。排查浪费一轮。
`curl --noproxy 127.0.0.1` 或 `NO_PROXY=127.0.0.1`；Python 要
`build_opener(ProxyHandler({}))`。这条已写进 `GET /` 自描述文档和 API.md。

**单实例插件的连带现象**：`Stop-Process` 后立刻 `Start-Process`，新进程会被单实例拦掉
（旧进程还在退出中），表现为"启动即退出、端口没监听"。重启应用要等 1–2 秒。

### 模型选择器（23:45）

把训练页的 3 张模型卡换成「任务 → 家族 → 规模」三级，覆盖全部 63 个可训练模型
（73 个 ID 里 sem/depth 各 5 个只能推理）。

- 数据层 `desktop/src/lib/models.ts`：**模型名的唯一来源**，页面不许再写 `"yolo26n"` 字面量。
  ID 规则 = `prefix + scale + ("" | "-seg" | "-cls")`，YOLOX/YOLOv3 的 prefix 自带连字符。
- 存"原始选择"而非"校验后的结果"：切任务时另两级可能失效（YOLOX 没有 `n`，它叫 `nano`），
  渲染时用 `resolveSelection()` 兜底。这样切走再切回，原家族还在。
- 家族数量随任务变（检测 7 / 分割 3 / 分类 3），用 `repeat(n, 1fr)` 动态列数，避免固定列数变形。
- 分类**故意阻断**：`dataset.rs` 只认 YOLO `images/+labels/`，没有 ImageNet `train/<类名>/`
  的扫描能力。选中后显示警告并禁用启动，而不是让人跑 20 分钟拿报错。

**验证手段**：把生成的 63 个 ID 逐条丢给 `montgomery.exe train --architecture <id>
--data /nonexistent --device cpu`，判据是走到 `NO_DATASET`（= clap 接受了这个 ID）而不是
`invalid value`。63/63 通过，无重复。比在 TypeScript 侧自测可信。
脚本：`spikes/qa/shot_model_picker.py`（CDP 点击 + 回读 DOM，8 组组合断言 + 截图）。

**试过并回退的**：操作条 `sticky bottom`。808px 视口下模型卡 450px、参数卡 190px，
吸底会压住正在编辑的输入框。按钮留在页尾，滚动顺序本身就是 选模型→调参→选设备→开始。
